1. Legal & Regulatory Compliance Framework
1.1 RBI Prepaid Payment Instrument (PPI) Compliance
Risk: If coins are purchasable, transferable, or cash-equivalent, they may be classified as a Prepaid Payment Instrument (PPI), requiring RBI authorization. The Draft PPI Directions explicitly clarify that loading of an instrument by digital currency does not constitute loading of a PPI, and reward points/in-game currency are excluded from PPI regulations. Marketplaces issuing loyalty or reward points in their accounts do not require RBI authorization.

Rule	Detail
Coins are earn-only	Users cannot purchase coins with real money
Coins are non-transferable	Cannot be sent to other users or converted to cash
Coins are non-cash-equivalent	Internal rewards unit, not a stored-value wallet
Cash payouts via regulated provider	RazorpayX/Cashfree Payouts only
Gift cards via reward provider	Xoxoday/QwikCilver/GyFTR only
No own INR wallet	Never hold user INR balances

2. Google Play Policy Compliance
2.1 Incentivized Installs — The Critical Rule
Google prohibits manipulation of ratings, reviews, or install counts through incentivized means, including incentivizing users to install other apps as the app's main functionality.[5†L14-L18] The policy explicitly states: "Developers must not attempt to manipulate the placement of any apps on Google Play. This includes, but is not limited to, inflating product ratings, reviews, or install counts by illegitimate means, such as fraudulent or incentivized reviews and ratings, or incentivizing users to install other apps as the app's main functionality."

Compliance Strategy:

Risk	Mitigation
App perceived as "install for coins"	Home screen shows rewards marketplace first
Offerwall dominant	Offerwall is ONE section under Earn tab
Store listing misleading	Describe broader rewards features (surveys, brand deals, coupons, products)
Campaign approval absent	Admin approval layer rejects non-compliant offers
Safe Home Screen Priority:

2.2 Play Store-Only Install Rule (New — Mandatory)
Requirement: All app/game install offers within the offerwall must redirect the user exclusively to the Google Play Store. No third-party APK sources, no direct APK downloads, no sideloading, no alternative app stores.

Rationale: Installing apps from outside the Play Store exposes users to security risks and violates the trust model of the Android ecosystem. The offerwall provider must be configured to serve only Play Store-linked install offers.

Aspect	Implementation
Offer source	Offerwall provider (Tapjoy, ironSource, etc.) must be configured to serve only Play Store install offers
User redirect	Clicking "Install" opens the Google Play Store listing (via market://details?id=<package_name> intent)
Attribution	Attribution SDK (AppsFlyer/Adjust) must track installs originating from Play Store
Backend validation	Backend must reject any postback where install source is not Play Store
Offer approval	Admin must verify the offer's landing destination before approval
User disclosure	Offer detail must state: "Installs must be completed via Google Play Store"
Technical Implementation:

text
Offer Click Flow:
User clicks "Start Offer"
   ↓
Backend creates click_id, logs offer source
   ↓
App opens Play Store via intent:
   market://details?id=<package_name>
   OR
   https://play.google.com/store/apps/details?id=<package_name>
   ↓
User installs from Play Store
   ↓
Attribution SDK detects install, sends postback
   ↓
Backend validates:
   - Install source = Play Store (via referrer data)
   - Click ID matches
   - No duplicate conversion
   ↓
Reward credited to PENDING
Referrer Validation:

Use the Google Play Install Referrer API to retrieve the install referrer string from the Play Store.

The referrer string should contain the click_id or a unique identifier that maps back to the offer click.

Backend must verify the referrer originates from Play Store before crediting rewards.

Offerwall Provider Configuration:

When setting up campaigns in Tapjoy/ironSource, select only "Install via Play Store" as the install source.

Block any campaigns that use direct APK downloads or third-party app store links.

Admin dashboard must display the install source for every offer and flag any non-Play-Store offers.

5.2 Offer Lifecycle (Server-Side) — Play Store-Only
text
Advertiser creates campaign (Play Store install only)
        ↓
Admin reviews & approves
        ↓
Tracking + attribution configured (Play Store install source)
        ↓
Offer becomes eligible (status: LIVE)
        ↓
User sees offer in app (with "Google Play Store" badge)
        ↓
User clicks CTA → click_id created
        ↓
App opens Play Store via intent:
   market://details?id=<package_name>
        ↓
User completes required event (install, registration, level)
        ↓
Provider verifies event (S2S postback)
        ↓
Backend receives postback:
  1. Validate signature
  2. Check idempotency (conversion_id)
  3. Map to user_id
  4. Check duplicate
  5. **Validate install source = Play Store**
  6. Create ledger entry (PENDING)
        ↓
Approval window passes / provider confirms
        ↓
Reward becomes AVAILABLE
        ↓
Notification sent to user
        ↓
User redeems (cash/gift card/product)
Referrer Validation Logic:

typescript
// Pseudocode for Play Store referrer validation
async function validateInstallSource(postback: Postback) {
  const referrer = await getPlayInstallReferrer(postback.device_id);
  
  // Referrer must originate from Play Store
  if (!referrer || !referrer.includes('play.google.com')) {
    throw new Error('Install source is not Play Store');
  }
  
  // Referrer must contain matching click_id
  if (!referrer.includes(postback.click_id)) {
    throw new Error('Click ID mismatch in referrer');
  }
  
  return true;
}
5.3 Wallet Ledger Rules
text
- Append-only: never UPDATE or DELETE ledger entries
- Balance = SUM of all valid entries
- Cached balance for performance only
- Every entry has: transaction_id, idempotency_key, reference_type, reference_id
- Reversals create NEW negative entry (never edit history)
- Redemption reserves coins → releases on failure
- Admin adjustments require dual authorization + audit log

8.2 Critical Constraints
sql
-- Wallet ledger: append-only (enforce via trigger)
-- Idempotency: unique per source
CREATE UNIQUE INDEX idx_ledger_idempotency
  ON wallet_ledger (idempotency_key);

-- Conversion: unique provider event
CREATE UNIQUE INDEX idx_conversion_event
  ON conversion_events (provider, conversion_id);

-- Withdrawal: unique idempotency
CREATE UNIQUE INDEX idx_withdrawal_idempotency
  ON withdrawals (idempotency_key);

-- Play Store only install source
ALTER TABLE offers ADD CONSTRAINT chk_install_source
  CHECK (install_source = 'play_store');

-- Landing URL must be Play Store
ALTER TABLE offers ADD CONSTRAINT chk_landing_url
  CHECK (landing_url LIKE 'https://play.google.com/store/apps/%'
         OR landing_url LIKE 'market://details?id=%');

10.3 Coin Economy
Parameter	Value
Coin name	Rewards Coin (RC)
Sample rate (UX prototype)	100 RC = ₹1
Production rate	Configurable, driven by campaign economics
Coin states	Pending → Available → Redeemed / Reversed
Expiry	Configurable (e.g., 12 months from credit)
Critical: Do NOT make 1 coin = ₹1 automatically. Coins are internal rewards units; value governed by published rules and campaign economics.

Outstanding coins × configured_coin_rate = Reward Liability
This is a liability on your books, not revenue

Breakage revenue	Recognized when coins expire

11. Fraud & Abuse Controls
11.1 Risk Signals
Signal	Action
Too many account creations / device cluster	Hold rewards, review
Rapid repeated offer starts	Throttle
Unusual conversion pattern	Pending/manual review
Payout velocity spike	Temporary withdrawal hold
Provider chargeback/reversal	Reverse associated reward
Referral abuse cluster	Block referral rewards
Payment mismatch	Do not fulfill order
Install source ≠ Play Store	Reject reward, flag user
11.2 Reward States
text
CLICKED → PENDING → VERIFIED → AVAILABLE → REDEEMED
Suspicious: PENDING_REVIEW | REJECTED | REVERSED | CHARGEBACK
11.3 Privacy Principle
Do not collect invasive device/application data merely because it could help fraud detection. Collect only what is necessary, disclose it accurately, and design the fraud system around server-side provider signals wherever possible.
