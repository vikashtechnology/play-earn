## Project

## Stack (fixed decisions)

- **Auth: Firebase Authentication** (email link, Google, phone OTP). Server-side ID token verification against Google's published signing certificates; no Supabase, no third-party auth.

**Local testing is two commands.** `npm run setup:env` builds `apps/api/.env` on a fresh machine — necessary because the file is git-ignored, so none of the sandbox configuration travels with the repo. It reads the Firebase identifiers from the committed `google-services.json` (public by design), generates `JWT_SECRET`/`OTP_HASH_SECRET` locally with 256 bits each and never prints them, sets the provider allowlist to `emailLink,google.com`, fills in the drafted policy versions and GitHub Pages URLs, leaves `SIGNUP_ENABLED=false`, writes mode `600` (with an explicit `chmodSync`, because `writeFileSync`'s `mode` only applies when it creates the file), and refuses to overwrite without `--force`. `npm run verify:local` then runs nine stages in dependency order — Node runtime, dependencies, `.env`, `config:check`, `npm test`, `npm run build`, `migrate`, `smoke:identity`, `smoke:http` — classifying each as PASS / FAIL / ENV / SKIP. **HTTP smoke test found four live defects (all fixed, all regression-covered).** `apps/api/scripts/smoke-http.js` (root `npm run smoke:http`) mounts the real `createApp()` handler and asserts on 21 routes; it exists because `src/server.js` refuses to boot unless Neon answers, which makes the HTTP surface untestable anywhere the database is unreachable. Each case accepts either a success status or the documented database-unavailable status, and no case may ever return 500 or drop the connection. Proven to catch what it was written for: with the fixes stashed it fails and the process dies; restored it reports 21/21.

1. **Any Bearer token on `/api/v1/payouts/:id` killed the whole API process.** `app.js` defined its own `defaultPayoutDependencies()` returning only `{identityRepository, identity}` — no `verifyToken` — which shadowed the correct default inside `payouts.js`. `authorizeUser` then called `undefined(...)`, throwing a `TypeError` in an async request handler; that is an unhandled rejection, fatal in Node, so a single `curl -H 'Authorization: Bearer x'` was a denial of service. `payouts.test.js` always injected its own dependencies, so the default wiring was never exercised. Fixed by exporting `defaultPayoutDependencies` from `payouts.js` and deleting the incomplete copy in `app.js`.
2. **No error boundary in `app.js`.** Any throw from any route crashed the process the same way. `routeRequest` is now wrapped in try/catch: log the stack server-side, respond 500 `Internal server error`, keep serving. Regression test asserts a deliberately throwing dependency yields 500 with no internals and that `/api/health` still answers afterwards.
3. **Driver messages were echoed to clients as 400.** The payouts catch-all returned `error.message` verbatim, so a Postgres failure leaked infrastructure detail with the wrong status. Added `isDatabaseUnavailableError(error)` in `src/db.js` (socket codes, SQLSTATE class 08/53300/57P0x/58030, and pg's own message patterns) and used it to return 503 `database_unavailable` with a generic message.
4. **Auth routes reported an unreachable database as a generic 500.** `sendIdentityError` now checks `isDatabaseUnavailableError` before falling through to 500, so `/auth/withdrawal/phone/verify` and `/auth/session/revoke` return 503 `database_unavailable` instead of `Unable to verify payout phone.` / `Unable to sign out.`

`authorizeUser` also refuses a non-function `verifyToken` with a 500 response rather than throwing, so a future wiring mistake degrades instead of crashing. Tests: 131 API + 10 validation pass (was 126 before this session's work).

## Decisions

-   India-only launch.
-   Android app + backend API + web admin.
-   Firebase Auth is the only identity provider; the API issues its own 15-minute HS256 session tokens and never trusts client-supplied identity.
-   Anonymous and custom Firebase tokens are rejected: every wallet must belong to a verifiable identity.
-   Neon PostgreSQL is the only database; TLS is enforced for Neon hosts.
-   Internal virtual coin currency.
-   Immutable/auditable wallet ledger; AdMob coins are in-app-only and excluded from cash redemption.
-   UPI/bank cash redemption where provider/business eligibility allows.
-   Gift cards/vouchers through an approved provider.
-   Physical products may support coins + cash.
-   Monetization through approved partner offers, ads, direct campaigns and brand deals.
-   Offer completion must be provider-verified.
-   Example placeholders never enable a feature: a `.env.example` value such as `https://your-domain.example/terms` counts as unpublished, so sign-in stays closed.
-   Provider integrations use adapters that fail closed.
-   Money/reward-changing admin actions are audited; authentication events are audited too.
-   Consent is versioned: the client must echo the exact Terms/Privacy versions it displayed.
-   Two Firebase UIDs may never share one email or phone; conflicts are rejected, not merged, and ownership is checked before any write.
-   Only a Firebase-attested contact counts: an unverified email cannot create an account, and a phone number sent in a request body can never grant Minimum KYC.
-   Offer visibility is decided in one place, so list and detail views cannot disagree and no sideload URL can be served.
-   Play Store compliance is a release gate.

## Constraints

No gambling/betting, fake engagement, fake conversions or policy-bypassing systems. Do not expose provider secrets to clients. Payment/business accounts must satisfy applicable age, KYC and legal requirements. Never claim guaranteed income.

**Fixed four real defects the emulator and end-to-end run exposed.** (1) `upsertFirebaseUser` only checked email/phone ownership on the *new account* path, so a returning sign-in or legacy-row adoption could take over a phone already owned by another account — ownership is now checked before any write, for every path. (2) `verifyWithdrawalPhone` fell back to a client-supplied `phone` when the token had no phone claim, which would have granted cash-payout KYC from a request body; it now requires `phone_number_verified: true` in the token and treats a body phone only as a cross-check (digits compared, mismatch rejected). (3) `normalizeFirebaseIdentity` never mapped `phone_number_verified`, so `phoneVerified` was always undefined, and Firebase reports phone auth as `sign_in_provider: "phone"` rather than `"phone.com"` — both would have broken phone sign-in and Minimum KYC in production; the claim is now mapped and provider spellings are normalized on both the identity and the configured allowlist. (4) `assertSessionUsable` silently skipped the revocation check when `issuedAt` was not a number, failing open; it now accepts epoch seconds, a `Date`, or an ISO string and rejects when the issue time cannot be determined.
